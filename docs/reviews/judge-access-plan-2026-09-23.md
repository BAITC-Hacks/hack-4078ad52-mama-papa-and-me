## Рекомендация

**Передавать жюри исходники для воспроизводимости и HTTPS-ссылку на размещённое приложение для полной проверки. Ключ OpenAI остаётся на сервере команды.** Жюри получает ограниченный пропуск приложения, не ключ OpenAI. Вызовы GPT-6 и поиск оплачивает API-проект команды; хостинг и диск оплачиваются отдельно.

Для текущей архитектуры наименьшая переделка — один постоянно работающий Next.js Node-сервис с постоянным диском для SQLite. Конкретный кандидат: платный Render Web Service + Persistent Disk. Это рекомендация для утверждения, а не незаметная смена ранее упомянутого Netlify. Если уже есть управляемый VPS с HTTPS, тот же способ размещения может быть проще покупки нового сервиса.

Схема: браузер жюри → HTTPS-приложение команды → движок/SQLite и OpenAI API → понятный результат в браузере. Секрет OpenAI не покидает сервер.

Render требует слушать 0.0.0.0 на PORT; диск сохраняет только свой каталог, доступен одной инстанции, недоступен в build/pre-deploy, а обновления сервиса с диском имеют короткий перерыв. Для небольшой демонстрации это приемлемая архитектура; масштабирование потребует другой базы. [Web Services](https://render.com/docs/web-services), [Persistent Disks](https://render.com/docs/disks).

Если платформа не умеет вводить код, передавать credential через предусмотренное организаторами поле/секрет. Запасной вариант — публичный демонстрационный режим с общей квотой на короткое окно. Публичную квоту могут исчерпать посторонние, она не гарантирует доступ судье. CAPTCHA и обязательный внешний OAuth могут препятствовать автоматическому судье.

## Что получает скачавший репозиторий

Исходники, синтетический датасет, тесты, пустой шаблон окружения и инструкции. Не получает локальный .env, ключ, API-баланс, текущую SQLite и сохранённые на компьютере сценарии. Это подтверждено README, .gitignore, src/config/index.ts.

Без ключа работают выбор, расчёт, бюджет, отчёт, сохранение в новой локальной БД. AI выдаёт обозначенное шаблонное объяснение. Это не полноценная живая AI-проверка.

Ключ нельзя безопасно «спрятать» внутри репозитория, Docker-образа, JS bundle или публичной переменной окружения. Извлечённый ключ можно использовать вне симулятора. Серверный пропуск разрешает лишь ограниченные операции приложения и отзывается без смены OpenAI-ключа.

## Почему не другие способы

| Вариант | Оценка |
| --- | --- |
| Целое приложение с серверным ключом | Основной: одна кодовая база, одинаковые расчёты/промпты, единый контроль расходов, жюри ничего не устанавливает |
| Netlify + внешняя Postgres/Supabase | Если Netlify обязателен: миграция storage, транзакционные квоты/lease во внешней БД, сверка Next.js адаптера и длительности HTTP handlers. Больше изменений |
| Отдельный AI-шлюз для локального клона | Запасной путь при обязательном clone/run: второй протокол, версии, аутентификация, сетевая зависимость |
| Отдельный временный ключ жюри | Только если допустима защищённая передача. Отдельный API-проект, минимальные права/лимит, отзыв после проверки; проверяющий может вызывать API в обход приложения |
| Туннель к ноутбуку | Для короткой согласованной демонстрации; зависит от ноутбука, процесса и соединения, Host/Origin и доступ всё равно нужно исправить |
| Ключ в Git или открытый универсальный прокси | Не подходит: неконтролируемое использование за счёт команды; обфускация не помогает |

Serverless не гарантирует сохранность локальных файлов между запросами; текущую SQLite нельзя считать постоянной базой Netlify. [Официальное объяснение stateless runtime](https://www.netlify.com/blog/2018/09/13/how-to-run-express.js-apps-with-netlify-functions/) — старый материал, используется только для принципа, не старых численных лимитов. Актуальные лимиты Netlify: synchronous 60 s, background 15 min. Background OpenAI не превращает Next Route Handler в Netlify Background Function. [Текущая конфигурация](https://docs.netlify.com/build/functions/configuration/).

Бесплатный Render теряет файловые изменения при рестарте/деплое/засыпании и не поддерживает постоянный диск. [Ограничения](https://render.com/docs/free). Точный тариф не назначен: нужен выбор compute/disk в аккаунте, OpenAI оплачивается отдельно. Бесплатный полный AI не обещаем.

## Подтверждённые изменения, необходимые в коде

| Участок | Сейчас | Что изменить до публикации |
| --- | --- | --- |
| package.json start | next start слушает 127.0.0.1 | Отдельная серверная команда 0.0.0.0/PORT; локальную оставить |
| src/app/api/http.ts body | Только loopback Host, http://host; guard применяется к body | Явный public origin, HTTPS, точные Host/Origin; не доверять произвольным X-Forwarded-* |
| GET analyses/[id] | pollAnalysis может создать платное объяснение | Проверять владельца/право/квоту каждой фазы; предпочтительно GET только читает, защищённый POST или worker продвигает задачу |
| storage | Сценарии общие, owner отсутствует, requestId глобален | ownerId, фильтры list/get/cancel/save, дедупликация внутри владельца |
| countRecent | Шесть запусков/минуту по client sessionId | Квота по серверному principal, общий лимит и лимит параллельности |
| SQLite/WAL | Файл на локальной FS, lease 90 s | Постоянный диск, runtime-миграции, SQLite backup/checkpoint; не копировать активный .sqlite отдельно от WAL |
| backend lifecycle | Два background этапа OpenAI; переход при browser poll, общий срок 180 s | Сохранять providerId/фазу, после рестарта читать без повторной генерации; закрытие вкладки не выдавать за гарантированную работу worker |
| status | aiConfigured — наличие ключа и флаг | Отличать configured от реальной успешной генерации; health не запускает платный AI |

UUID задания не заменяет авторизацию. Host/Origin не идентифицируют клиента: HTTP-клиент может выставить их вручную. Владельца нужно проверять до возврата duplicate requestId, иначе чужой анализ может раскрыться до основного запуска.

## Доступ и квоты: минимальная реализация

1. Разделить local/judge режимы; loopback по умолчанию сохраняется.
2. Ограниченные пропуски: случайный token высокой энтропии, хранение hash, срок, квота, отзыв. Не передавать token в query URL или коммите.
3. Браузер вводит код один раз; сервер выдаёт HttpOnly Secure SameSite cookie. Автоматический клиент использует scoped Bearer token через защищённое поле окружения. Это token приложения, не OpenAI.
4. Сервер определяет ownerId. Client sessionId — только диалог внутри владельца. Все analyses/scenarios проверяют owner; бесплатный simulate и минимальный status могут остаться публичными с ограничением нагрузки.
5. До первого внешнего вызова транзакционно резервировать анализ и оба платных этапа. Повтор requestId не расходует новый слот. Смена sessionId/браузера не обновляет квоту.
6. При исчерпании запрещать и start, и незарезервированный запуск explanation при poll. Готовый результат можно читать после исчерпания. Не освобождать квоту автоматически при неопределённом исходе оплачиваемого запроса.
7. Ограничить параллельность, общий вход, историю и исследовательский текст. Сохранить output caps; задать конечный предел web_search. max_tool_calls есть в установленном SDK, поддержку модели подтвердить при реализации. Инструкция «несколько источников» не является техническим пределом.
8. Ошибку доступа/квоты объяснять честно; бесплатный движок остаётся доступен. После окна оценки отозвать пропуски/выключить AI. Отмена не гарантирует возврат расходов.

Например, Q анализов при нынешнем протоколе — не более 2Q создаваемых response, если нет автоматических повторов. Это предел количества, не фиксированная стоимость. Денежную оценку считать по действующим ценам токенов и поиска, сверять с usage/биллингом. Общий Q и бюджет должен выбрать владелец до размещения.

## Ограничение расходов у провайдера

Отдельный API-проект оценивания, серверный ключ, минимальные права. Настроить alerts и, если доступно в аккаунте, **Enforce a hard limit**, проверить применённое значение. По актуальной документации hard limit блокирует запросы с 429 после достижения учитываемого расхода, но применяется с задержкой, возможно небольшое превышение. Alerts запросы не останавливают. [OpenAI Spend limits](https://developers.openai.com/api/docs/guides/spend-limits).

Настройки аккаунта владельца не проверялись и не менялись. В этой работе OpenAI-вызовов не выполнялось. Общий лимит API-проекта дополняет собственные серверные квоты, а не заменяет их.

## Запасной путь: ограниченный AI-шлюз

Только если организаторы требуют clone/run. Локальный backend отправляет ScenarioInput/вопрос по HTTPS на сервис команды с application token. Шлюз принимает известные версии/меры и пересчитывает отчёт своим engine; не доверяет клиентским cost/score/evidence. Возвращает AnalysisView и job ID; poll/cancel требуют того же principal.

Не делать универсальный OpenAI-compatible proxy, произвольные модели/URL/tools/system prompts или пересылку пользовательского Authorization в OpenAI. Контракт ограничен городским анализом, размеры/квоты проверяются сервером. Локально нужны URL и scoped token; OpenAI key не передаётся. Требуются поддержка сохранения удалённого анализа, совместимость версий, handling недоступного шлюза. Это отдельный адаптер, не одна замена baseURL.

## Сквозная приёмка до передачи ссылки

- Внешняя сеть и новый браузер: HTTPS, расчёт, один настоящий final, сохранение/открытие.
- Без пропуска: платный start и продвижение/чтение чужого analysis запрещены; simulate доступен согласно политике.
- Два пропуска: изоляция списка/истории/сохранений, запрет чужих read/cancel и requestId.
- Смена sessionId, параллельные starts и новые вкладки не обходят квоту; резервирование атомарно.
- Рестарт сохраняет БД, задачи и квоты; не создаёт дубль генерации. Деплой вне окна судейства.
- Исчерпание между фазами блокирует незарезервированную работу, но не чтение готового ответа.
- Ключ отсутствует в bundle/network/логах; при проверке значение не выводится.
- Ошибки провайдера/квоты/storage честно показаны, расчёт остаётся доступен.
- Smoke проходит по public URL; отдельный реальный анализ подтверждает AI. Smoke сам не доказывает готовность доступа.
- Тесты/линтер/типы/build изменённых модулей, Linux и persistent disk на выбранном хостинге.
