# Роли команды: «Аким на 5 часов»

Документ распределяет разработку MVP между тремя участниками. Все работают в одном Next.js + TypeScript репозитории. Главный принцип стыковки: сначала согласовать типы данных и API-контракт, затем делать части параллельно.

## Участник 1 — Frontend и пользовательский сценарий

### Цель

Собрать интерфейс, в котором пользователь без инструкции понимает, как выбрать пять мер, следит за бюджетом и видит последствия сценария.

### Зона владения

- src/app/page.tsx
- src/components/
- стили и клиентское состояние выбора

### Задачи

1. Сделать главный экран с названием, кратким описанием, стартовым бюджетом и базовым Score.
2. Отобразить каталог мер карточками: ID, направление, стоимость, тип «район/город», лаг и эффекты.
3. Для районной меры добавить выбор одного района; для городской — не показывать выбор района.
4. Показывать пять слотов выбора, текущую сумму и остаток бюджета.
5. Блокировать или объяснять очевидно недопустимые выборы: шестую меру, повтор и превышение бюджета.
6. Подключить результат POST /api/simulate.
7. Показать Score, прирост, районные баллы, изменение показателей и критические значения.
8. Добавить график или визуальное сравнение до/после с Recharts.
9. Подключить POST /api/explain; при отсутствии объяснения показать состояние загрузки и резервный текст.
10. Сохранить черновик выбора в localStorage, если это не мешает основному потоку.

### Готово, когда

- Можно пройти сценарий от стартового экрана до отчёта.
- Нельзя отправить выбор менее или более чем из пяти мер.
- Ошибки API и загрузки AI видны пользователю и не ломают приложение.
- На экране результата различимы общий балл и состояние отдельных районов.
- UI принимает районные и городские меры в согласованном формате.

### Не брать на себя

- Не реализовывать формулу Score в браузере.
- Не считать лаги и синергии в компонентах.
- Не помещать AI API-ключ в клиентский код.

## Участник 2 — Backend, данные и расчётный движок

### Цель

Сделать единственный источник истины для валидации сценария и численного расчёта.

### Зона владения

- src/lib/data/
- src/lib/engine/
- src/app/api/simulate/route.ts

### Задачи

1. Перенести исходные данные районов, доли населения, показатели, меры и веса в JSON/TypeScript-конфигурацию.
2. Описать типы District, Measure, Selection, ScenarioReport.
3. Реализовать валидатор:
   - ровно пять выбранных мер;
   - нет повторов;
   - стоимость не выше 100;
   - не больше двух мер одного направления;
   - у районной меры ровно один допустимый район;
   - у городской меры район не указывается;
   - проверяются все несовместимости из задания.
4. Реализовать применение эффектов:
   - районные меры применяются только к выбранному району;
   - городские меры применяются ко всем районам;
   - эффект умножается на (8 − L) / 8;
   - синергии применяются фиксированно в районе первой меры пары;
   - итоговые показатели обрезаются в диапазон 0–100.
5. Рассчитать районные оценки, средневзвешенный городской балл, слабейший район, N_crit и итоговый Score.
6. Возвращать детальный отчёт с базовыми и итоговыми значениями, дельтами, стоимостью, синергиями и критическими значениями.
7. При невалидном запросе возвращать причины по отдельности, не запускать AI и не выдавать Score.
8. Зафиксировать контрольные значения: базовый Score 52,56 и приведённый пример около 56,54.

### Готово, когда

- Все числовые результаты получаются в одном модуле и одинаково используются UI и AI.
- Каждое правило валидатора возвращает понятное сообщение.
- Контрольный пример имеет расход 95 и Score около 56,54.
- Входные данные валидируются до выполнения расчёта.

### Не брать на себя

- Не обращаться к LLM для арифметики.
- Не округлять промежуточные значения в расчётах; округление только для отображения.
- Не менять значения датасета или веса без согласования всей команды.

## Участник 3 — LLM, интеграция, README и демо

### Цель

Добавить объяснение сценария, сохранить воспроизводимый запуск и подготовить убедительную демонстрацию.

### Зона владения

- src/lib/ai/
- src/app/api/explain/route.ts
- README.md
- .env.example
- демо-сценарий

### Задачи

1. Сделать серверный маршрут POST /api/explain, который принимает ScenarioReport от расчётного движка.
2. Вызвать LLM через официальный серверный SDK; модель задавать конфигурацией окружения.
3. Передавать LLM исходный и итоговый Score, районные и показательные дельты, вклад мер, риски и синергии.
4. Просить модель отвечать структурированно: краткий вывод, сильные стороны, риски, рекомендации.
5. Запретить модели пересчитывать показатели или заявлять числовые факты, отсутствующие в отчёте.
6. Ограничить рекомендации существующими мерами каталога; если альтернативный набор не был рассчитан движком, не представлять его как гарантированно допустимый или лучший.
7. Добавить шаблонный fallback, чтобы результат работал без ключа API или при ошибке модели.
8. Хранить ключ только в серверном окружении; добавить в .env.example названия нужных переменных без секретных значений.
9. Написать README: требования, установка, запуск, переменные окружения, архитектура, формула, правила, известные ограничения и демонстрационный сценарий.
10. Подготовить 2–3-минутное демо: исходное состояние, выбор примера, Score, изменения Нуры, синергия, затем одно нарушение для демонстрации валидатора.

### Готово, когда

- AI получает только готовый расчётный отчёт.
- Ошибка или отсутствие API-ключа не ломает симуляцию.
- В README можно найти команды запуска и понять, откуда берутся числа.
- Демонстрация использует контрольный сценарий из задания.

### Не брать на себя

- Не менять математику и ограничения самостоятельно.
- Не просить модель самостоятельно выбирать неподтверждённые числовые эффекты.
- Не коммитить API-ключи и другие секреты.

## Общий контракт между участниками

### Запрос симуляции

    {
      "selections": [
        { "measureId": "M7", "districtId": "Нура" },
        { "measureId": "M12", "districtId": null }
      ]
    }

Передаются ровно пять объектов. districtId задаётся для районной меры и равен null для городской.

### Успешный отчёт движка

Минимальный набор полей:

    {
      "valid": true,
      "totalCost": 95,
      "remainingBudget": 5,
      "baseScore": 52.56,
      "score": 56.54,
      "delta": 3.99,
      "districtScores": [],
      "indicatorChanges": [],
      "measureContributions": [],
      "synergies": [],
      "criticalIndicators": []
    }

Фактические названия полей нужно закрепить в общей TypeScript-схеме в начале работы. Значения baseScore, score и delta в примере — для демонстрации формата; движок хранит достаточную точность и округляет только при выдаче или отображении.

### Ошибка валидации

    {
      "valid": false,
      "errors": [
        "Выберите ровно 5 мер",
        "Превышен бюджет: 108 из 100"
      ]
    }

Текстовые сообщения можно улучшать, но фронтенд не должен зависеть от точной формулировки: для логики использовать коды ошибок, например WRONG_SELECTION_COUNT, BUDGET_EXCEEDED, INCOMPATIBLE_MEASURES.

## Порядок интеграции

1. Все участники согласуют типы Selection и ScenarioReport.
2. Участник 2 первым добавляет JSON данных и заглушку POST /api/simulate.
3. Участник 1 собирает интерфейс по API-контракту, временно используя мок-ответ.
4. Участник 3 собирает POST /api/explain с мок-отчётом и fallback.
5. После готовности движка подключаются реальные ответы и исправляются расхождения.
6. Перед демо участники прекращают крупные изменения интерфейсов и вместе проходят контрольный сценарий.

## Общие правила работы

- Не редактировать чужую зону владения без короткого согласования.
- Сначала договориться о полях контракта, потом менять их синхронно.
- Числа рассчитывает движок; UI отображает, LLM объясняет.
- Исходные данные и ограничения считаются общими для всех команд.
- Для MVP не добавлять регистрацию, отдельную базу данных или сложную систему рейтингов.
- Если времени не хватает, приоритет: валидатор и Score → выбор мер → экран результата → AI-объяснение → визуальные улучшения.
