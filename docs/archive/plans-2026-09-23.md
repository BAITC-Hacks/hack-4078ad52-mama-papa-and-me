## 1. Продукт и объём

Игрок выбирает пять инициатив и видит распределение бюджета, изменения районов, итоговый Astana Quality of Life Score и компромиссы. Все пять направлений доступны; выбирать по одной мере в каждом не требуется по прямому решению владельца.

Первоначальный порядок «mock-фронтенд → просмотр → backend» изменён последующим запросом: реализовать сразу весь локальный MVP с Astra medium и живым веб-поиском. Просмотр владельцем остаётся следующим этапом обратной связи, но больше не блокирует реализацию backend.

Это учебная модель, не официальный индекс и не прогноз ВВП/здоровья. Движок считает, AI объясняет доверенные числа и исследует реальный контекст. Проверка JSON и идентификаторов не доказывает истинность свободного текста. Нужна экспертная оценка для реальных управленческих решений.

## 4. Данные и точные правила

Источник — предоставленный DOCX. Его полное текстовое содержание и шесть таблиц сохранены в [docs/data/dataset-source.md](../data/dataset-source.md); там же SHA-256 оригинала. Числа в этой копии не изменены. Программно проверены суммы весов, долей населения, оценки пяти районов и контрольный пример.

- Районы: Есиль, Алматы, Сарыарка, Байконур, Нура; доли населения 0.27, 0.24, 0.20, 0.13, 0.16.
- Показатели: T1/T2 — транспорт, E1/E2 — экология, S1/S2 — социальная инфраструктура, B1/B2 — безопасность, C1/C2 — городской сервис. Значения 0–100, больше всегда лучше.
- Ровно 5 уникальных мер; бюджет 100; не более 2 мер одного направления. Остаток бюджета не сгорает и не даёт бонуса.
- У районной меры выбран один допустимый район; у городской район не указан, эффект применяется ко всем пяти районам.
- M1 + M3 запрещены при любых районах; M4 + M7 и M5 + M13 запрещены при совпадении района.
- Горизонт H = 8 кварталов. Эффект меры умножается на `(8 − L) / 8`. Это итоговая модель на горизонте, не полноценная поквартальная динамика.
- Синергии: M1 + M2 → T1 +2 в районе M1; M10 + M12 → B1 +2 в районе M10; M5 + M6 → E2 +2 в районе M5. Бонус применяется один раз и не масштабируется лагом.
- Все эффекты и синергии суммируются, затем каждый показатель обрезается до 0–100. Порядок выбора не влияет на результат. Отрицательный эффект M11 на T1 сохраняется.
- Вес показателей в порядке T1, T2, E1, E2, S1, S2, B1, B2, C1, C2: 0.10, 0.10, 0.09, 0.11, 0.11, 0.11, 0.09, 0.09, 0.10, 0.10.

```text
I'[d,k] = clip(I[d,k] + Σ(effect[m,k] × (8 − L[m]) / 8) + synergy[d,k], 0, 100)
D[d]    = Σ(weight[k] × I'[d,k])
D_avg   = Σ(populationShare[d] × D[d])
N_crit  = количество пар «район × показатель», где I'[d,k] < 40
Score   = 0.7 × D_avg + 0.3 × min(D[d]) − N_crit
```

Score не приравнивается к ВВП и не обрезается повторно до 0–100. Округление — только при отображении. Невалидный набор возвращает причины без Score и без обращения к LLM. Исходный город показывается отдельно от валидации отправленного сценария.

## 7. Контракты и доверенные данные

Selection содержит measureId и districtId (null для города). ScenarioInput: версии и selections. POST /api/simulate принимает также mode preview/final. Лишние поля отклоняются строгой схемой; цены/эффекты/Score рассчитываются сервером. Невалидный набор получает HTTP 400 и причины, без Score и без LLM.

ScenarioReport содержит базу, итоговые показатели, стоимость/остаток, Score/delta, критичность, вклады мер после лага, синергии, clipping и factIds. Для неполного preview score/delta=null. Вклад в показатели не следует представлять как аддитивный вклад в нелинейный Score.

POST /api/analyses получает тот же выбор, kind step/chat/final, вопрос, контекст и UUID requestId/sessionId. Сервер пересчитывает отчёт; для previousSelections добавляет проверенные факты с префиксом previous. GET статуса и DELETE отмены работают по локальному ID. POST/GET /api/scenarios сохраняют/открывают серверный отчёт. Точные схемы — в [contracts](../../src/contracts/README.md).

SQLite хранит сценарии и задания; AI-задания содержат модель, reasoning, promptVersion, usage, источники и отчёт с версиями. Дедупликация по requestId не является семантическим кэшем одинаковых вопросов: такой кэш пока не реализован. SQL скрыт в storage; ошибка сохранения не отменяет уже показанный расчёт.

## 8. AI и интернет

Изменение портфеля пересчитывает preview и отменяет старое ожидание, но не запускает новый платный анализ. Вопрос советнику и кнопка итогового разбора запускают chat/final. Простое открытие карточки, переключение карты, reset и загрузка примера запрос не создают.

Один анализ — два background response: исследование с обязательным web_search, затем Structured Outputs с реестром цитат. Модель gpt-6-astra, effort medium, максимум 5000/7000 output tokens соответственно, retries=0. Промпт urban-advisor-3 требует учитывать контекст Астаны и различать игровые числа, исследования и гипотезы. Нельзя выводить ВВП или зарплаты из обеспеченности школами: таких переменных нет.

JSON и factIds/sourceIds проверяются. Источники context обязательны; URL берутся из url_citation, а не из произвольного текста. Эти проверки не гарантируют семантическую корректность; анализ экспертом и расширенная серия evals остаются дальнейшей работой. [AI-спецификация](../ai-design.md) описывает промпт и ограничения.

Лимиты: шесть стартов в минуту на сессию, до 3000 символов вопроса, 180 секунд ожидания. Браузер опрашивает статус; без опроса переход к следующему этапу не происходит. По дедлайну новая платная фаза не начинается; уже завершённый финальный ответ возвращается и при позднем опросе. Отмена и прерванный запуск не вызывают автоматического платного повтора. БД хранит состояние, UI восстанавливает ID задачи после перезагрузки вкладки.

## 9. Мировые практики

[Справочник источников](../research/README.md) сохранён. Runtime выполняет поиск по вопросу/мерам, а не подменяет его справочным текстом. Промпт предпочитает исследования и официальные материалы, проверяет контекст климата, сезонности, обслуживания и экономики. Неизвестные местные данные отмечаются ограничением. Публикация программы не доказывает причинный эффект.

Исследования не меняют коэффициенты датасета. Для реалистичного градостроительного режима нужны местные данные, калибровка, причинная модель, интервалы неопределённости и более длинный горизонт. Это отдельный будущий этап.

## 10. Ограничения и следующий объём

Многопользовательские аккаунты, рейтинг команд, случайные события, презентации и автоматический поиск улучшений не реализованы. Пока нет фонового worker вне опросов браузера, денежного лимита API или полностью автоматической проверки истинности текста. Все пользователи начинают одинаково; события в базовом режиме отсутствуют.
