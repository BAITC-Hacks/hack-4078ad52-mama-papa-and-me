# План разработки: «Аким на 5 часов»

## 1. Идея продукта

Команда получает одинаковый виртуальный город, синтетические данные пяти районов и бюджет в 100 условных единиц. Игрок выбирает ровно пять городских инициатив, назначает районы для районных мер и видит, как решения меняют показатели и итоговый Astana Quality of Life Score.

Симулятор помогает обсуждать компромиссы: городская мера охватывает все районы, районная мера точечно помогает выбранному району, а отложенный эффект уменьшает результат инициативы в рамках горизонта моделирования. Итоговая формула отдельно учитывает слабейший район и критические показатели, поэтому нельзя оценивать сценарий только по среднему городскому баллу.

Это сценарная модель на синтетических данных, а не прогноз фактического состояния города.

## 2. Правила MVP

- Все пользователи начинают с одинаковыми исходными данными и бюджетом 100.
- Нужно выбрать ровно 5 уникальных мероприятий.
- Общая стоимость не может превышать бюджет.
- У районной меры должен быть выбран ровно один район; у городской меры район не выбирается.
- Не более 2 мер одного направления; по текущим правилам это гарантирует охват минимум 3 направлений.
- Запрещены указанные несовместимые пары.
- Эффект меры умножается на долю реализации: (8 − лаг) / 8.
- Городской эффект применяется ко всем районам, районный — к выбранному району.
- Синергии применяются фиксированным бонусом и не масштабируются лагом.
- Каждый показатель после эффектов ограничивается диапазоном 0–100.
- Невалидный набор не получает Score; интерфейс показывает конкретную причину.

### Решение по неоднозначности требований

В общем описании говорится о пяти направлениях, но детальные правила требуют пять мер и не более двух на направление, а приведённый пример не включает транспорт. Для MVP принимается детальная трактовка: ровно пять инициатив минимум из трёх направлений. Если организаторы подтвердят, что обязательны все пять направлений, валидатор нужно поменять до реализации: при ровно пяти инициативах это будет по одной мере на направление.

## 3. Пользовательский сценарий

1. Пользователь открывает сценарий с бюджетом 100 и стартовым Score 52,56.
2. Из каталога выбирает пять мер.
3. Для районных мер выбирает район; стоимость и остаток бюджета обновляются сразу.
4. Интерфейс заранее показывает конфликты, повторный выбор и нарушения лимитов.
5. Пользователь запускает расчёт.
6. Результат показывает новый Score, изменение к базе, оценки районов, показатели до/после, критические значения, стоимость и сработавшие синергии.
7. AI формирует объяснение сильных сторон, рисков и возможных улучшений на основе отчёта движка.

## 4. Расчётная модель

Для каждого показателя района применяется сумма эффектов мероприятий с учётом лага и синергий, после чего значение ограничивается диапазоном 0–100.

Оценка района — взвешенная сумма его десяти показателей. Городская оценка D_avg — сумма оценок районов с весами их доли населения. N_crit — число пар «район × показатель» со значением строго меньше 40 после применения эффектов.

Итоговая формула:

    Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit

Расчёты по исходным данным и примеру из задания перепроверены программно:

| Сценарий | Расход | D_avg | Минимум D района | N_crit | Score |
|---|---:|---:|---:|---:|---:|
| Без действий | 0 | 56,8624 | 49,18 | 2 | 52,55768 ≈ 52,56 |
| M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка | 95 | 58,0776 | 52,9625 | 0 | 56,54307 ≈ 56,54 |

Для второго сценария прирост составляет примерно 3,99 балла (около +4,0). Синергия M10 + M12 добавляет +2 к B1 в Нуре. Примерный набор допустим по стоимости, количеству мер, лимиту направлений и несовместимостям.

## 5. Рекомендуемый стек

| Слой | Технология | Назначение |
|---|---|---|
| Full stack приложение | Next.js App Router + TypeScript | UI и серверные API-маршруты в одном проекте |
| UI | React, Tailwind CSS, shadcn/ui | Экран выбора, карточки мер, бюджет и результат |
| Визуализация | Recharts | Сравнение районов и показателей до/после |

| Исходные данные | Версионируемые JSON-файлы | Идентичный синтетический сценарий для всех |
| Расчёт | Чистые TypeScript-функции | Валидация, эффекты, синергии, Score |
| AI | OpenAI API через серверный JavaScript/TypeScript SDK | Объяснение уже рассчитанного результата |
| Состояние в браузере | localStorage | Черновик выбора без настройки базы данных |
| Репозиторий | GitHub | Совместная разработка и README |

Для MVP отдельная база данных не нужна. Общий рейтинг команд можно добавить позже с серверным хранилищем, если останется время.

## 6. Архитектура

    Браузер / Next.js UI
        ├── POST /api/simulate
        │       └── Zod → валидатор → движок расчёта → отчёт с числами
        └── POST /api/explain
                └── LLM получает отчёт → текстовое объяснение

Расчётный движок не зависит от LLM. Если LLM недоступна или не настроен ключ, результат симуляции всё равно отображается, а текст строится из простых шаблонов. Секретный ключ модели хранится только в серверной переменной окружения.

## 7. API-контракт

### POST /api/simulate

Запрос:

    {
      "selections": [
        { "measureId": "M7", "districtId": "Нура" },
        { "measureId": "M12", "districtId": null }
      ]
    }

Ответ при успехе должен включать:

- **valid**;
- **totalCost**, **remainingBudget**;
- **baseScore**, **score**, **delta**;
- оценки районов до и после;
- показатели районов до и после;
- вклад выбранных мер;
- сработавшие синергии;
- критические показатели.

Ответ при ошибке включает **valid: false** и массив понятных причин. Ошибки должны охватывать количество мер, повторы, бюджет, неверный или отсутствующий район, лишний район у городской меры, лимит направлений и несовместимости.

### POST /api/explain

Получает рассчитанный отчёт, а не исходный выбор без расчёта. Возвращает поля **summary**, **strengths**, **risks**, **recommendations**. Числа в ответе AI должны совпадать с переданным отчётом. Рекомендации могут ссылаться только на каталог мер; найденные альтернативные сценарии по возможности рассчитываются движком отдельно.

## 8. План на пять часов

| Время | Результат |
|---|---|
| 0:00–0:20 | Создать проект, зафиксировать правила и API-контракт |
| 0:20–1:30 | Параллельно: UI, расчётный движок и серверная AI-интеграция |
| 1:30–2:30 | Соединить UI с /api/simulate и показать полный результат |
| 2:30–3:20 | Подключить /api/explain и шаблонный fallback |
| 3:20–4:15 | Проверить бюджет, повторы, районы, лимиты, несовместимости и контрольный сценарий |
| 4:15–5:00 | README, публикация при наличии времени, репетиция демо |

Подробные персональные зоны ответственности и точки интеграции описаны в файле agents.md.

## 9. Приёмочный список MVP

- [ ] В приложении зафиксированы одинаковые данные и бюджет 100.
- [ ] Можно выбрать ровно пять уникальных мер.
- [ ] Районные и городские меры обрабатываются по-разному.
- [ ] Превышение бюджета и другие нарушения блокируются с объяснением.
- [ ] Все перечисленные эффекты, лаги, синергии, несовместимости и клиппинг реализованы.
- [ ] Изменение выбора может изменить итоговый Score.
- [ ] Результат показывает влияние по районам и направлениям.
- [ ] LLM объясняет только отчёт расчётного движка.
- [ ] Без LLM остаётся работоспособный экран результатов.
- [ ] Проект можно запустить по README без закрытых данных.

## 10. Демонстрация жюри

1. Показать стартовый бюджет 100 и Score 52,56.
2. Собрать проверенный пример из пяти мер стоимостью 95.
3. Показать Score 56,54, исчезновение двух критических значений в Нуре и сработавшую синергию.
4. Изменить одну меру или район и показать, что расчёт меняется.
5. Попытаться превысить бюджет или выбрать конфликтную пару, чтобы показать валидатор.
6. Завершить AI-объяснением, которое комментирует уже рассчитанные факты.
